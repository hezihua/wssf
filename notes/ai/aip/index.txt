15:T4700,<p>本文整理自项目讨论，说明开源版 AIP（Artificial Intelligence Platform）闭环在做什么、和传统系统差在哪、以及当前实现如何把 Agent 的读写面收束到 Ontology / Action。</p>
<hr>
<h2>一、核心闭环</h2>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark-dimmed"><code data-language="text" data-theme="github-dark-dimmed" style="display: grid;"><span data-line=""><span>Raw Data → Ontology（业务对象）→ Agent（编排）→ Action（受控写回）</span></span></code></pre></figure>
<p>目标不是复刻绚丽界面，而是让「死表」变成「活的业务对象」：大模型能读、能写，但必须走平台规则与安全边界。</p>
<p>当前仓库大致对应：</p>

<td>✅（轻量）</td>

<h2>二、和「传统写回按钮」的差别</h2>
<h3>传统</h3>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark-dimmed"><code data-language="text" data-theme="github-dark-dimmed" style="display: grid;"><span data-line=""><span>用户改表单 → 点保存 → API 直接 UPDATE → 完成</span></span></code></pre></figure>
<p>写操作绑在 UI 上，一次请求里改库。</p>
<h3>Infini / AIP</h3>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark-dimmed"><code data-language="text" data-theme="github-dark-dimmed" style="display: grid;"><span data-line=""><span>Agent 理解意图</span></span>
<span data-line=""><span>  → 生成 Action（pending，尚未改业务对象）</span></span>
<span data-line=""><span>  → Casbin：谁能提、谁能批</span></span>
<span data-line=""><span>  → Human-in-the-loop（如 carol 批准）</span></span>
<span data-line=""><span>  → 真正写回 Object</span></span></code></pre></figure>
<table>
<thead>
<tr>
<th></th>
<th>传统写回按钮</th>
<th>Action + HITL</th>
</tr>
</thead>
<tbody>
<tr>
<td>改库时机</td>
<td>点击即写</td>
<td>批准后才写</td>
</tr>
<tr>
<td>AI 角色</td>
<td>容易变成「代你点保存」</td>
<td>只能提交受控 Action</td>
</tr>
<tr>
<td>审计</td>
<td>多为日志</td>
<td>有独立 Action 记录</td>
</tr>
</tbody>
</table>
<hr>
<h2>三、「传统也能审批」——那 AIP 还多什么？</h2>
<p>传统审批流里同样可以：alice 提交 → admin/carol 批准 → 再写库。<br>
<strong>有没有 HITL，不是 AIP 的独家发明。</strong></p>
<p>真正多出来的是约束面，尤其是对 AI：</p>
<table>
<thead>
<tr>
<th></th>
<th>传统审批</th>
<th>AIP / Infini</th>
</tr>
</thead>
<tbody>
<tr>
<td>提交物</td>
<td>表单 / 流程实例</td>
<td>本体上声明的 <strong>ActionType</strong>（强类型参数）</td>
</tr>
<tr>
<td>写库</td>
<td>流程节点里跑业务代码 / SQL</td>
<td><strong>只能</strong>执行已注册 Action</td>
</tr>
<tr>
<td>AI 通道</td>
<td>常另开接口直写，与人走两套路</td>
<td><strong>人和 Agent 写库都走 Action</strong></td>
</tr>
<tr>
<td>读侧</td>
<td>多在提交后卡权限</td>
<td>提交前 Agent 只能看见授权 Objects</td>
</tr>
</tbody>
</table>
<p>一句话：</p>
<ul>
<li>传统也能做人审。</li>
<li>AIP 把「可写什么」收成 Ontology 上的 Action；LLM <strong>只能提议这些 Action</strong>；读写落在同一套对象语义和权限里。</li>
</ul>
<p>若去掉 Agent、只留人工「提议 Action → 批准」，外表会像传统审批；<strong>对 AI 的统一写网关与机读能力目录</strong>才是差异点。</p>
<hr>
<h2>四、点击「运行 Agent」打了哪些接口？</h2>
<p>前端会连续调用：</p>
<ol>
<li>
<p><strong><code>POST /agent/run</code></strong><br>
真正跑 Agent：读对象、提议 Action（写入 pending）。</p>
</li>
<li>
<p><strong><code>GET /actions?status=pending</code></strong><br>
刷新右侧 HITL 列表。</p>
</li>
</ol>
<p>批准写回是另一次操作：</p>
<ul>
<li><strong><code>POST /actions/{id}/approve</code></strong></li>
</ul>
<p>不是「运行 Agent」本身自动改库。</p>
<hr>
<h2>五、「读对象、提议 Action、pending」分别是什么？</h2>
<h3>读哪个对象？</h3>
<p>以「将工单 t_100 标记为已解决」为例（heuristic）：</p>
<ol>
<li>读 Ontology schema（有哪些 Object / Action）</li>
<li>读业务对象 <strong><code>Ticket</code> / <code>t_100</code></strong></li>
<li><code>submit_action(update_ticket_status, …)</code></li>
</ol>
<p>受 Casbin 约束：例如 alice 只能看到 <code>c_001</code> 相关对象。<br>
Demo 里 ObjectType 目前主要是 <code>Ticket</code>、<code>Customer</code>。</p>
<h3>提议是临时的吗？</h3>
<p><strong>不是纯内存临时变量</strong>，而是落库的 Action 记录（表 <code>ontology_actions</code>）：</p>
<ul>
<li>状态先为 <code>pending</code></li>
<li>有稳定 <code>id</code>（UUID）</li>
<li>批准后才改业务 Object；拒绝则对象不变</li>
</ul>
<p>「临时」指的是 <strong>还没写业务对象</strong>，不是请求结束就丢。</p>
<h3>入职入库 / 离职出库可以吗？</h3>
<p>可以，同一套模式。工单只是 demo，换成人事即：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark-dimmed"><code data-language="text" data-theme="github-dark-dimmed" style="display: grid;"><span data-line=""><span>ObjectType: Employee</span></span>
<span data-line=""><span>ActionType: onboard_employee   → 入库</span></span>
<span data-line=""><span>ActionType: offboard_employee  → 出库</span></span></code></pre></figure>
<p>闭环不变：读对象 → 提议 Action（pending）→ 人批 → 写回。<br>
前提：先在本体登记 ActionType、定好参数与权限，并实现 approve 后的执行器。</p>
<hr>
<h2>六、和「以前一个功能写一个 API」的差别</h2>
<p>不完全是「以前给人，现在给 Agent」。</p>
<h3>以前</h3>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark-dimmed"><code data-language="text" data-theme="github-dark-dimmed" style="display: grid;"><span data-line=""><span>POST /tickets/{id}/resolve</span></span>
<span data-line=""><span>POST /employees/onboard</span></span>
<span data-line=""><span>…</span></span></code></pre></figure>
<p>每个接口各自校验、权限、写库；前端 / 脚本 / Agent 各自对接不同 URL。</p>
<h3>现在</h3>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark-dimmed"><code data-language="text" data-theme="github-dark-dimmed" style="display: grid;"><span data-line=""><span>Ontology 登记 Object / Action</span></span>
<span data-line=""><span>统一写入口：POST /actions（或工具 submit_action）</span></span>
<span data-line=""><span>能力目录：GET /ontology/agent-context</span></span></code></pre></figure>
<table>
<thead>
<tr>
<th></th>
<th>散装 API</th>
<th>Ontology / Action</th>
</tr>
</thead>
<tbody>
<tr>
<td>能力发现</td>
<td>靠文档 / Prompt</td>
<td><code>agent-context</code> 机读</td>
</tr>
<tr>
<td>写入口</td>
<td>每功能一个 endpoint</td>
<td>统一 Action 网关</td>
</tr>
<tr>
<td>服务对象</td>
<td>人、Agent 常两套</td>
<td>人与 Agent 共用语义</td>
</tr>
</tbody>
</table>
<p><strong>本质</strong>：给业务能力建「机读目录 + 统一写网关」，而不是简单把 API 的调用方从人换成 Agent。</p>
<hr>
<h2>七、传统 API 仍适用的场景（Ontology / Action 不是银弹）</h2>
<p>Ontology + Action 适合「业务语义强、要给 Agent 安全动手、要统一审计/审批」的路径。<br>
它<strong>不能、也不该</strong>取代所有接口。下面这些场景，继续用（或优先用）普通 API 更合适：</p>
<h3>更适合散装 / 专用 API 的情况</h3>
<table>
<thead>
<tr>
<th>场景</th>
<th>原因</th>
</tr>
</thead>
<tbody>
<tr>
<td>高 QPS、低延迟读写</td>
<td>列表分页、搜索、实时推送；走 Action + HITL 过重</td>
</tr>
<tr>
<td>简单 CRUD / 管理后台</td>
<td>字段编辑、配置页；人为主、无 Agent 参与时，直接 API 更清晰</td>
</tr>
<tr>
<td>文件上传、流式、WebSocket</td>
<td>传输形态特殊，不适合塞进 Action payload</td>
</tr>
<tr>
<td>登录、OAuth、Webhook 回调</td>
<td>协议型接口，不是「业务对象动作」</td>
</tr>
<tr>
<td>批量 ETL / 数仓管道</td>
<td>Airbyte、dbt、作业调度；属于数据层，不是 Agent 写回</td>
</tr>
<tr>
<td>跨系统集成（对方只认固定 REST）</td>
<td>对外契约已定；可对内再接到 Action execute</td>
</tr>
<tr>
<td>健康检查、指标、内部运维</td>
<td><code>/health</code>、metrics；与业务 Ontology 无关</td>
</tr>

<h3>更适合 Ontology / Action 的情况</h3>
<table>
<thead>
<tr>
<th>场景</th>
<th>原因</th>
</tr>
</thead>
<tbody>
<tr>
<td>Agent 要读懂业务并提议变更</td>
<td>需要机读的 Object / Action 目录</td>
</tr>
<tr>
<td>写操作风险高、要人审</td>
<td>入职、调岗、关停资源、改关键状态等</td>
</tr>
<tr>
<td>多端（人 + Agent + 将来其它客户端）共用写语义</td>
<td>避免每人一套写接口</td>
</tr>
<tr>
<td>要按对象做细粒度授权</td>
<td>Casbin 挂在 Object / Action 上更自然</td>
</tr>
</tbody>
</table>
<h3>共存方式（推荐心智）</h3>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark-dimmed"><code data-language="text" data-theme="github-dark-dimmed" style="display: grid;"><span data-line=""><span>对外 / 专用 API          Ontology 读 + Action 写</span></span>
<span data-line=""><span>（集成、CRUD、上传…）  →  （Agent、高风险业务变更）</span></span>
<span data-line=""><span>         ↘                    ↙</span></span>
<span data-line=""><span>           同一套 domain service</span></span></code></pre></figure>
<ul>
<li><strong>不是</strong>「所有功能都登记成 Action」</li>
<li><strong>而是</strong>「Agent 能动的手、以及要统一治理的写，走 Action；其余该 API 还 API」</li>
<li>Action 的 <code>execute</code> 往往 <strong>调用</strong> 已有业务服务，而不是把业务逻辑重写一遍</li>
</ul>
<p>若强行把分页查询、文件上传也做成 Action，只会增加延迟和复杂度，收益很小——<strong>银弹不存在，边界比口号重要</strong>。</p>

<h2>八、<code>/ontology/agent-context</code> 是什么？</h2>
<p><strong>不是文件，是 HTTP 接口。</strong></p>
<ul>
<li>地址：<code>GET http://127.0.0.1:8000/ontology/agent-context</code></li>
<li>路由：<code>src/infini_ontology/api.py</code> → <code>get_agent_context</code></li>
<li>数据：<code>registry.agent_context()</code>（<code>ontology/registry.py</code>）</li>
<li>作用：把已注册的 Object / Link / Action（并按 Casbin 过滤可 submit 的 Action）收成 JSON，供 Agent 规划</li>
</ul>

<p>也可在 <a href="http://127.0.0.1:8000/docs">http://127.0.0.1:8000/docs</a> 中调试。</p>
<hr>
<h2>九、「读写面收束到 Ontology/Action」怎么实现？</h2>
<p>不是靠 Agent 自觉，而是多层硬约束：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark-dimmed"><code data-language="text" data-theme="github-dark-dimmed" style="display: grid;"><span data-line=""><span>Agent（LLM / heuristic）</span></span>
<span data-line=""><span>   │ 只能调白名单工具</span></span>
<span data-line=""><span>   ▼</span></span>
<span data-line=""><span>get_ontology_schema / list_objects / get_object / follow_link / submit_action</span></span>
<span data-line=""><span>   │</span></span>
<span data-line=""><span>   ▼</span></span>
<span data-line=""><span>Registry 校验 + ObjectStore + ActionService + Casbin</span></span>
<span data-line=""><span>   │</span></span>
<span data-line=""><span>   ▼</span></span>
<span data-line=""><span>真正改库只在 Action approve → execute</span></span></code></pre></figure>
<ol>
<li>
<p><strong>工具白名单</strong>（<code>agent/tools.py</code>）<br>
无 SQL、无任意 PATCH；LLM 只能 <code>bind_tools</code> 上述工具。</p>
</li>
<li>
<p><strong>读路径</strong><br>
必须是已注册 ObjectType；实例再过 Casbin 过滤。</p>
</li>
<li>
<p><strong>写路径</strong><br>
只能 <code>submit_action</code> → <code>registry.get_action</code>（未登记即失败）→ 参数校验 → Casbin submit → 通常只写 pending；改库要 approve。</p>
</li>
<li>
<p><strong>Prompt</strong>（软约束）<br>
强调写必须走 <code>submit_action</code>；硬约束仍是工具层 + 服务层。</p>
</li>
</ol>
<hr>
<h2>十、还要不要写业务接口给 Ontology 用？</h2>
<p><strong>要有业务逻辑，但不一定再给人/Agent 各暴露一套 REST。</strong></p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark-dimmed"><code data-language="text" data-theme="github-dark-dimmed" style="display: grid;"><span data-line=""><span>业务逻辑（建员工、关账号、改状态…）</span></span>
<span data-line=""><span>        ↑</span></span>
<span data-line=""><span>Ontology / Action（登记 + 校验 + 权限 + HITL）</span></span>
<span data-line=""><span>        ↑</span></span>
<span data-line=""><span>Agent / 前端（读 Object + submit_action）</span></span></code></pre></figure>
<ul>
<li>Ontology：契约与入口</li>
<li>业务实现：Action <code>execute</code> 时调用的 domain service / 内部 API</li>
</ul>
<p>当前 demo 的业务写在 <code>ActionService._dispatch</code> 内；生产中更常见是 execute 转调已有服务。</p>
<table>
<thead>
<tr>
<th>要准备</th>
<th>不必重复</th>
</tr>
</thead>
<tbody>
<tr>
<td>ObjectType / ActionType 登记</td>
<td>给 Agent 一人一个平行业务 URL</td>
</tr>
<tr>
<td>Action 参数、权限、HITL</td>
<td>Agent 直连旧 CRUD</td>
</tr>
<tr>
<td>execute 里的真实业务逻辑</td>
<td>两套完全不同的写路径</td>
</tr>
</tbody>
</table>
<p>新功能推荐顺序：<strong>登记 Action → 实现 executor →（按需）HITL</strong>，而不是先给 Agent 再开平行 API。</p>
