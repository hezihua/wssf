后端架构全景解析

jimmy · 2026-5-21

一、入口层（流量接入与治理）

1.1 客户端入口

  • Web、iOS、安卓、PC 多端接入
  • 流量来源区分：正常用户 vs Bot（机器人） vs 第三方 调用

1.2 流量平台

  • 攻击清洗：防御 DDoS、恶意请求
  • 转发：流量分发到后端服务

1.3 网关层（Gateway）

  • 服务治理：统一入口管理
  • 监控 & 统计：实时流量、性能监控
  • Cache：缓存加速，减轻后端压力
  • 网关作为单一模块承接所有入口流量，再路由到后端服务

二、资金层（钱）

2.1 支付对账平台

  • 处理所有资金往来、交易流水对账

2.2 道具/抽奖/履约

  • 虚拟道具发放
  • 抽奖活动逻辑
  • 订单履约闭环

2.3 支付渠道

  • 银行、微信支付（WX）、支付宝
  • 对接多渠道支付，保障资金通路稳定

2.4 To B 商家平台

  • 面向商家的资金管理、结算、提现等功能
  • 需防范 洗钱、羊毛党 等风险

三、用户层

3.1 内部营销平台

  • 用户增长、活动策划、营销推广
  • 核心目标：增长 / 获客

3.2 审核平台

  • 内容/行为审核，保障平台合规
  • 用户发布的内容、交易行为等都需要过审

3.3 用户数据报表

  • BI 展示：业务数据可视化
  • 支撑运营决策

四、数据层

4.1 数据平台

  • 提交 SQL、报表需求
  • 支撑业务数据查询与分析

4.2 安全

  • 数据安全策略、权限管控
  • 敏感数据加密、防泄漏

4.3 存储基础设施

组件 用途
OSS 对象存储，静态资源（图片、文件等）
RDS 关系型数据库，结构化数据存储
ADB 分析型数据库，大数据计算

4.4 监控要求

"这些平台都是要监控好的" —— 所有基础设施和业务平台都需要完善的监控告警体系，保障稳定性。

五、风控层

5.1 安全审核

  • 资料变更：身份证号、手机号等敏感信息变更监控
  • 资金来往：交易行为风控
  • 消息识别：区分 机 / 人，识别异常消息（Bot 行为）
  • 支持 人工审核 介入

六、多媒体层

6.1 WebRTC

  • 语音、视频 实时通信
  • 信令 服务：连接建立、状态同步
  • 属于底层能力，一般不展开细讲

七、运维与部署层（CI/CD）

7.1 部署环境

环境 说明
线下 开发/测试环境
线上 生产环境
预上线 灰度/Staging 环境

7.2 操作系统

  • iOS、Windows、Linux

7.3 基础设施

  • 告警 & 监控：全链路可观测性
  • ECS：云服务器
  • 机房：物理服务器托管
  • K8s：容器编排，现代化部署方式
  • 域名：DNS 管理

7.4 运维关注点

  • SQL：数据库性能、慢查询优化
  • 高可用：服务容灾、故障自动切换
  • 内存、CPU、网络：核心资源监控

八、后端固定组件选型

这些是后端开发中相对固定的几类组件，技术选型围绕它们展开：

8.1 语言

  • 选型相对灵活，根据团队技术栈和场景选择

8.2 网络框架

  • 需完成交流（通信）
  • 明确哪一层、使用什么协议
  • 区分 关系型 / 非关系型 数据库
  • 区分 分析型 / 事务型 场景
  • 关注 内存 / 外存 使用

8.3 数据库

  • 关系型：MySQL、PostgreSQL 等
  • 非关系型：Redis、MongoDB 等

8.4 异步执行

  • 完成异步执行任务
  • 定时 / 延时 任务调度

8.5 消息队列

  • MQ（通用消息队列）
  • Kafka：高吞吐日志/事件流处理

8.6 对象存储

  • 静态资源、文件存储

8.7 支付底座

  • 支付核心能力封装，供业务层调用

8.8 流量网关

  • 灰度：灰度发布，渐进式上线
  • 开关：功能开关（Feature Toggle），快速回滚/启用功能

十、核心设计要点总结

  1. 入口统一：网关作为单一模块收口所有流量，便于治理和监控
  2. 风险防控：资金层重点防范洗钱、羊毛；流量层防御攻击；风控层识别机/人
  3. 数据驱动：BI 报表支撑业务决策，数据平台提供查询能力
  4. 监控全覆盖：从基础设施到业务平台，监控告警不可或缺
  5. 灰度与开关：流量网关支持灰度发布和功能开关，保障发布安全
  6. 组件选型灵活：语言、框架相对灵活，但消息队列、存储、网关等组件类型相对固定
