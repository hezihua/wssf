15:T1d45,<h2>一、项目启动：需求与排期</h2>
<h3>1.1 需求来源</h3>
<p>需求可能来自多个渠道：</p>
<ul>
<li><strong>销售</strong> 提出的客户需求</li>
<li><strong>内部</strong> 业务方的需求</li>
<li><strong>现场</strong> 问题反馈</li>
<li><strong>下游公司</strong> 的对接需求</li>
</ul>
<h3>1.2 评估与排期流程</h3>
<pre><code>需求 → 评估 → 立项 → 排期
</code></pre>
<h3>1.3 团队角色与职责</h3>
<p>作为项目负责人，你需要对以下人员<strong>全部负责</strong>：</p>
<ul>
<li><strong>售前</strong>：技术方案预研、可行性评估</li>
<li><strong>运维集成</strong>：环境搭建、部署上线</li>
<li><strong>测试</strong>：功能验证、质量保证</li>
<li><strong>上下游</strong>：接口对接、联调协调</li>
</ul>
<h3>1.4 时间节奏</h3>
<ul>
<li><strong>下班早</strong> → <strong>上班</strong>（意味着工作节奏紧凑，需要高效推进）</li>
<li><strong>1个月</strong> 内要出<strong>成果</strong>，时间压力很大</li>
</ul>
<hr>
<h2>二、技术调研与选型</h2>
<h3>2.1 调研流程</h3>
<pre><code>设计讨论 → 调研 → 调研完成
</code></pre>
<h3>2.2 核心关注点</h3>
<p>调研阶段需要确定：</p>
<ul>
<li><strong>组件/客户端/编写</strong>：技术组件选择、客户端方案、编码规范</li>
<li><strong>服务架构</strong>：整体服务架构设计</li>
<li><strong>业务理解</strong>：深入理解业务需求，技术为业务服务</li>
</ul>
<h3>2.3 技术栈选型参考</h3>
<h4>通信协议</h4>
<table>
<thead>
<tr>
<th>类型</th>
<th>技术</th>
<th>适用场景</th>
</tr>
</thead>
<tbody>
<tr>
<td>第三方对接</td>
<td>HTTP客户端</td>
<td>外部API调用</td>
</tr>
<tr>
<td>内部服务</td>
<td>gRPC</td>
<td>高性能内部通信</td>
</tr>
</tbody>
</table>
<h4>数据库与ORM</h4>
<ul>
<li><strong>DB</strong>：数据库选型</li>
<li><strong>JDBC</strong>：Java数据库连接</li>
<li><strong>MyBatis</strong>：持久层框架</li>
</ul>
<h4>Web服务框架</h4>
<ul>
<li><strong>API / WebAPI / REST API</strong>：接口风格</li>
<li><strong>Netty</strong>：高性能网络框架</li>
<li><strong>Tomcat</strong>：传统Servlet容器</li>
</ul>
<h4>统一处理层</h4>
<ul>
<li><strong>异常</strong>：全局异常处理</li>
<li><strong>错误码</strong>：统一错误码规范</li>
<li><strong>过滤</strong>：请求过滤、权限校验</li>
<li><strong>拦截</strong>：AOP拦截、日志记录</li>
</ul>
<hr>
<h2>三、设计阶段</h2>
<h3>3.1 设计原则</h3>
<ul>
<li><strong>API 切分</strong>：合理划分接口粒度</li>
<li><strong>统一</strong>：保持设计一致性</li>
</ul>
<h3>3.2 沟通与理解</h3>
<ul>
<li><strong>售前</strong> 引导 → <strong>同一业务理解</strong> → <strong>一致</strong></li>
<li>确保团队对业务语义理解一致，避免后期返工</li>
</ul>
<h3>3.3 核心设计文档</h3>
<table>
<thead>
<tr>
<th>文档</th>
<th>内容</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>DB设计</strong></td>
<td>数据库表结构、索引、关系设计</td>
</tr>
<tr>
<td><strong>设计</strong></td>
<td>整体架构设计文档</td>
</tr>
<tr>
<td><strong>ERD</strong></td>
<td>实体关系图</td>
</tr>
</tbody>
</table>
<h3>3.4 语义与规范</h3>
<ul>
<li><strong>语义</strong>：接口命名、字段含义要清晰明确</li>
<li><strong>坑</strong>：避免歧义，减少后期理解成本</li>
<li><strong>体会</strong>：积累经验，形成团队共识</li>
</ul>
<hr>
<h2>四、开发阶段</h2>
<h3>4.1 开发原则</h3>
<ul>
<li><strong>开发 → 不重复 → 库</strong>：代码复用，封装公共库</li>
<li><strong>一味开发 → 测试 → 方向</strong>：避免盲目开发，通过测试验证方向</li>
</ul>
<h3>4.2 架构设计要点</h3>
<ul>
<li><strong>结构</strong>：清晰的模块划分</li>
<li><strong>抽象</strong>：提取公共逻辑</li>
<li><strong>原子性</strong>：最小功能单元</li>
<li><strong>后期扩展</strong>：预留扩展点，应对需求变更</li>
</ul>
<h3>4.3 协作与沟通</h3>
<ul>
<li><strong>2个</strong>：与上下游/上上级保持沟通</li>
<li><strong>难</strong>：独立负责时沟通成本高</li>
<li><strong>多</strong>：需要协调的关联方多</li>
</ul>
<hr>
<h2>五、部署与运维</h2>
<h3>5.1 部署方式演进</h3>
<pre><code>部署 → 淘汰 → K8S/云
</code></pre>
<ul>
<li>传统部署方式逐渐被淘汰</li>
<li>现代部署转向 <strong>K8S</strong> 和云平台</li>
</ul>

<h3>5.3 环境配置</h3>
<ul>
<li><strong>脚本</strong>：部署脚本自动化</li>
<li><strong>库</strong>：依赖库管理</li>
<li><strong>文件</strong>：配置文件管理</li>
<li><strong>路径</strong>：文件路径规范</li>
<li><strong>配置</strong>：环境配置分离</li>
<li><strong>IP / Port</strong>：网络地址管理</li>
<li><strong>网络</strong>：网络策略、安全组</li>
</ul>
<h4>容器化工具</h4>
<ul>
<li><strong>Docker</strong>：容器化部署</li>
<li><strong>Compose</strong>：多容器编排</li>
</ul>
<hr>
<h2>六、配置管理</h2>
<h3>6.1 配置分离原则</h3>
<ul>
<li><strong>配置</strong> 与 <strong>代码/组件/网络</strong> 分离</li>
<li><strong>单独</strong>：独立管理，不混在一起</li>
</ul>
<h3>6.2 配置传递</h3>
<pre><code>组件/网络 → 单独配置
</code></pre>
<h3>6.3 启动参数</h3>
<ul>
<li><strong>启动</strong> 时传入 <strong>参数</strong></li>
<li>通过启动参数实现环境差异化配置</li>
</ul>
<hr>
<h2>七、联调与测试</h2>
<h3>7.1 联调流程</h3>
<pre><code>联调 → 细节修改
</code></pre>
<h3>7.2 原因</h3>
<ul>
<li>设计阶段只能大方向比较稳，不要出现大的bug,联调阶段进行细节调整，事务的发展规律</li>
</ul>
<h3>7.3 评审与上线</h3>
<ul>
<li><strong>评审</strong>：代码评审、方案评审</li>
<li><strong>向上级展示</strong>：展示成果</li>
</ul>
<hr>
<h2>八、独立负责项目的关键要点</h2>
<h3>8.1 全流程掌控</h3>
<p>作为唯一后端负责人，需要覆盖完整链路：</p>
<pre><code>需求 → 调研 → 设计 → 开发 → 测试 → 部署 → 运维
</code></pre>
<h3>8.2 核心能力要求</h3>
<ol>
<li><strong>技术广度</strong>：熟悉前后端联调、数据库、部署运维</li>
<li><strong>业务深度</strong>：理解业务语义，技术方案贴合业务</li>
<li><strong>沟通协调能力</strong>：对接售前、测试、上下游多方</li>
<li><strong>时间管理能力</strong>：1个月内交付，节奏紧凑</li>
</ol>
<h3>8.3 避坑指南</h3>
<ul>
<li>避免"一味开发"，要边开发边验证</li>
<li>设计阶段确保团队"同一业务理解"</li>
<li>配置与代码分离，便于环境切换</li>
<li>提前考虑"后期扩展"，避免架构僵化</li>
